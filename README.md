# OpenShadow

**中文版** | [英文版](README_EN.md)

> **Shadow 持有连续性。**  
> 模型和运行时可以替换，属于用户的长期状态不应该随之消失。

OpenShadow 是一个**本地优先、运行时无关的个人 AI 连续性与控制层**。

它不试图成为另一个“大而全”的智能体，而是把身份、记忆、任务、能力、规则、历史与世界状态从具体模型和智能体中解耦出来，让 Hermes、DSH、Claude、Codex 以及未来的新运行时都可以作为可替换的推理与执行资源接入。

## 为什么需要 OpenShadow

模型更新很快，但人的生活、项目和经验是长期连续的。今天大多数个人 AI 系统仍然把状态绑定在某个产品、会话或框架里，因此换模型、换智能体、换设备，往往意味着重新建立上下文、迁移工具和恢复配置。

OpenShadow 关注的不是“怎样再做一个更聪明的助手”，而是：

> **如果未来十年模型、智能体框架和交互方式不断变化，哪些东西应该一直留下来？**

答案是那些真正属于用户的长期资产：

- 身份、偏好、约束与信任边界；
- 正在进行的任务、项目状态与语义检查点；
- 可追溯的长期记忆、历史证据与决策经验；
- 已经接入的设备、服务、工具与自动化能力；
- 对现实世界的当前认知与长期规则。

这些资产应该能够被下一代模型继续使用，而不是随着上一代产品一起被丢弃。

## 设计愿景

### 1. 连续性属于用户，而不是运行时

运行时只负责推理和执行。任务、记忆、权限和历史的事实源由 Shadow 持有。

因此更换 Hermes、DSH 或未来的新运行时，应该更像更换一个执行引擎，而不是迁移整套个人 AI。

### 2. 越容易被替换的东西，越远离核心

模型、提示词、检索引擎、交互界面和智能体框架都会快速变化；原始历史、任务状态、长期规则和个人能力则很难重新获得。

OpenShadow 希望形成一个稳定的“薄腰”：外围技术可以快速替换，靠近用户的长期状态尽量稳定。

### 3. 全天候存在，但按需使用智能

持续运行不意味着持续运行大模型。

Shadow 采用分层智能：确定性规则优先处理明确事件；`Pulse` 作为极小的本地注意力层全天候常驻；只有真正复杂、重要或不确定的问题才逐级唤醒本地通用模型和专业运行时。

### 4. 能力应该成为可复用基础设施

邮箱、日历、服务器、家庭设备、文件系统等能力一旦接入 Shadow，就不应该被某一个智能体独占。

新的智能体只需要通过统一规则获得被授权的能力，而不必重新接鉴权、权限、状态和工具链。

> **一次接入，持续复用；一次积累，被未来所有智能体继承。**

长期来看，OpenShadow 希望把 AI 使用从一种持续消费的服务，逐渐变成一种能够积累记忆、能力、经验和治理规则的**个人数字基础设施**。

> **十年后模型已经完全不同，但你的 AI 不需要重新认识你。**

```text
人 / 数字世界 / 物理世界
          │
          ▼
交互与事件入口
聊天 · 语音 · 邮件 · 日历 · 文件 · 设备 · 服务器
          │
          ▼
┌──────────────────────────────────────────┐
│              SHADOW CORE                 │
│          连续性与控制层                   │
│                                          │
│ 身份 / 规则      事件 / 世界状态          │
│ 任务 / 检查点    记忆策略 / 记忆代理器     │
│ 上下文编译器     运行时接口 SRI            │
│ 能力网关 / 台账  调度器 / Pulse            │
│                                          │
│ 长期资产：                                │
│ 记忆 · 任务 · 能力 · 规则 · 历史 / 状态   │
└──────────────────────────────────────────┘
          │
          ├─ 可替换运行时
          │  Hermes · DSH · Claude · Codex · 未来运行时
          │
          ├─ 可替换记忆引擎
          │  Mem0 · LangMem · Graphiti · 未来引擎
          │
          ├─ 能力提供者
          │  家庭 · 电脑 · 服务器 · 文件 · 邮件 · 日历 · 网络
          │
          ▼
PostgreSQL · 原始证据 · 任务产物
```

### 分层智能

```text
第 0 层  确定性规则
         │
         ▼
第 1 层  Shadow Pulse
         极小本地模型 / 分类器，全天候常驻
         │
         ▼
第 2 层  本地通用模型
         按需唤醒
         │
         ▼
第 3 层  通用或专业运行时
         Hermes · DSH · Claude · Codex
```

`Pulse` 以事件驱动为主。心跳只用于状态校验、补偿和没有自然事件源的条件检查，而不是周期性唤醒大模型询问“有没有事情要做”。

## 核心边界

| Shadow 持有 | 优先复用或外包 |
| --- | --- |
| 身份、规则与信任边界 | 智能体循环与规划 |
| 规范化任务与语义检查点 | Hermes、DSH、Claude、Codex |
| 原始证据与规范化记忆契约 | Mem0、LangMem、Graphiti |
| 记忆策略、记忆代理器与上下文编译 | 向量、嵌入和图检索实现 |
| 事件与世界状态 | Home Assistant 等设备驱动 |
| 能力注册、能力网关与执行台账 | 邮件、日历、浏览器、服务器等能力实现 |
| SRI、运行时路由与升级 | 具体模型与模型服务 |
| 长期调度与 Pulse 策略 | 聊天平台、语音栈和消息网关 |

一个简单的判断标准是：

> **必须跨模型、跨运行时、跨设备或跨年份保持一致的状态，属于 Shadow；其余能力优先复用成熟系统。**

## v0.1 最小可行版本

第一版不追求完整的个人 AI 产品，只验证这套连续性架构是否成立。

### 核心范围

- **连续性状态**：事件、世界状态、任务、语义检查点、原始证据与规范化记忆；
- **动态运行**：确定性规则、可替换 `Pulse`、事件驱动唤醒、调度与等待任务恢复；
- **运行时抽象**：SRI、Hermes 适配器、DSH 适配器、上下文编译器；
- **能力与治理**：能力注册表、能力网关、规则、审批、幂等与执行台账；
- **基础设施**：PostgreSQL、pgvector、命令行、最小管理界面和本地单机部署。

### 必须通过的验证

| 场景 | 验证目标 |
| --- | --- |
| 运行时连续性 | Hermes 中断后，DSH 能从语义检查点继续同一个任务 |
| 跨运行时记忆 | 一个运行时形成的长期记忆能被另一个运行时正确使用 |
| 自主事件处理 | 没有用户提示时，事件也能触发判断、任务与执行 |
| 分层智能 | 大量低价值事件在规则或 Pulse 层结束，只有少量任务升级 |
| 运行时升级 | 候选运行时可回放、灰度、晋升和回滚，而用户状态无需迁移 |
| 任务感知记忆 | 召回围绕当前任务决策价值，而不是简单向量前若干条 |
| 副作用安全 | 崩溃与重试不会重复执行已经完成的现实动作 |
